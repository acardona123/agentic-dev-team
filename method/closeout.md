# Story closeout

What the dispatching session hands Alex once QA passes a story, so that closing
it is reading and confirming rather than remembering.

Triggered by `CLAUDE.md` rule 10. Read this file at that moment; do not carry it
in context the rest of the time.

The Human gate in [definition-of-done.md](definition-of-done.md) is the source of
truth for *what* must happen. This file is only about *who says it and when*, so
that no item on that gate depends on Alex remembering it unprompted.

It runs in two beats, because the middle of it is a phone demo that only Alex can
perform and nothing can be prefilled until its outcome is known.

---

## Beat 1 — QA returns READY FOR ALEX

Hand him, in one message:

1. **The verdict**, per AC, and any defect QA named without failing — including
   what is now recorded in `## Spotted` rather than fixed.
2. **The demo script**, taken from QA's UNVERIFIABLE-HERE steps, not rewritten.
   Say which step covers which AC, and which single step is the one that would
   most embarrass us if skipped. Post it as a PR comment too, so he can read it
   off the phone instead of scrolling a terminal.
3. **The triggers QA reported fired**, read from its verdict's
   `triggers fired:` line ([ADR-0017](adr/0017-adr-revisit-trigger-register.md)).
   `none` is said in one line, not skipped.
   - **One QA marked `(caused by this branch)` comes first, as a decision, not
     a drafted entry** (ADR-0017 §3(c)): merging is what makes it fire, so it
     is settled before the merge command is handed over. Say which trigger,
     what the merge would cause, and his three options: hold the merge (for
     ADR-0004's undemoed-stories signal, demo first); send the branch back to
     its owner so it no longer fires; or merge knowing it fires — then, and
     only then, it is drafted as below, with his reason in the entry.
   - **Every other one**: draft a one-line `## Backlog` entry for him to
     confirm or reject:
     `**Revisit ADR-00xx** — trigger "<its line in adr-triggers.md>" fired (QA on <ID>, <date>): <QA's evidence>. Owner: architect.`
     Confirmed, it is committed on the item's own branch, before the merge, as
     `<ID>: backlog — revisit ADR-00xx`, appended to `## Backlog` for the PO to
     place ([ADR-0014 §6](adr/0014-work-item-types.md#6-only-a-merged-pr-reaches-develop)).
     Rejected, draft a `## Spotted` line instead — the ADR, the evidence, and
     his reason — committed the same way, so the same evidence is not raised
     again. It does not block the merge.

   Neither touches `adr-triggers.md`: a planning commit is confined to
   `## Backlog` and `## Spotted`, and a State changes only in the diff of the
   item that handles the trigger.
4. **The merge command**, ready to paste. He may tell you to run it; that is
   allowed and the Human gate says so explicitly. Merging because *you* judged
   the work ready is not.
5. **Anything still unpushed**, named. A local-only commit is a thing he cannot
   see and will not remember.

Then stop. Do not prefill the log yet — half its content is the demo's outcome.

## Beat 2 — Alex reports the demo results

Whether it passed or failed, first say plainly which ACs that settles.

**If any step failed:** it goes back to `dev` with QA's report and his
observation, not a fresh specification. The story stays where it is. Beat 2
restarts when it comes back green.

**If every step passed**, hand him one message containing:

1. **A prefilled `method/log/S<n>.md`.** `Demonstrated commit:` filled with D's
   SHA — D is the commit the story PR's merge left `develop` at, the one he
   demoed (`gh pr view <PR#> --json mergeCommit -q .mergeCommit.oid`), so he
   never has to remember it. `Asked for`, `What came back` and `What QA caught`
   written from the record. `What I'd specify differently` and `Method change`
   drafted too — but marked, in the message, as proposals for him
   to confirm or rewrite, because [log/README.md](log/README.md) says the log is
   his and `Method change` is the point of the file. Draft them from what actually
   happened, including anything the *method* got wrong, not only the app.
2. **The remaining Human-gate items, in order, as pasteable commands** —
   generated by walking [definition-of-done.md](definition-of-done.md)'s Human
   gate, not from memory. The story PR is already merged and D demoed, so what
   remains is this sequence ([ADR-0014 §2](adr/0014-work-item-types.md#2-closing-a-story)).
   Present each step when it can run, never all up front for him to track:
   1. **Now — fast-forward `main` to D**, never past it:
      `git fetch origin && git switch main && git merge --ff-only <D> && git push`
   2. **Once he has confirmed the drafts in items 1 and 3 — the closeout PR.**
      Marking the story Done and writing the log are not separate steps any
      more; both are this one commit, holding only the bookkeeping: the story's
      block (Status → Done, ACs ticked, PR recorded), `method/log/S<n>.md`, the
      PORTING row, and any `## Spotted` / `## Backlog` entries from the demo.
      ```bash
      git switch develop && git pull --ff-only
      git switch -c story/S<n>-closeout
      # write the confirmed drafts, then:
      git add app/backlog.md method/log/S<n>.md method/PORTING.md
      git commit -m "S<n>: closeout"
      git push -u origin story/S<n>-closeout
      gh pr create --base develop --title "S<n>: closeout" --body "Bookkeeping for S<n>; demonstrated commit <D>."
      ```
   3. **Once the PR's `closeout` check is green — merge it**, with the same
      merge command as the story PR's in Beat 1, filled with this PR's number.
      There is no QA run: there is no acceptance criterion to judge. `develop`
      moves past D; `main` does not, and picks the closeout up with the next
      demoed fast-forward.
3. **The bookkeeping that has no line on the gate** but is always there:
   observations he made during the demo that belong in `## Spotted` or as a new
   unrefined backlog item; whether any decision taken during the story still
   lacks an ADR (rules 5 and 8); whether `## Review` is now empty; and the
   story's row in [PORTING.md](PORTING.md)'s method-changes table, tagged
   `core` or `project` — that table is only useful if it is appended per
   story rather than reconstructed later.
4. **The next work item** — the top of `## Backlog`, in the PO's order — and,
   if a `/clear` is advised ([token-budget.md](token-budget.md)), the exact
   self-contained prompt to paste after it, so the next session starts from the
   repo rather than from his memory.

He may tell you to do all of it. Do it, then report what actually landed — refs,
what is pushed, and the gate re-run on the merged result rather than the branch's
earlier green.

## Task closeout

A task ([ADR-0014](adr/0014-work-item-types.md)) has no demo, so it has no Beat 2
and no log. When QA returns READY FOR ALEX on a task, Beat 1 only, adapted:

1. **The verdict**, per completion criterion — and, for each one QA marked
   UNVERIFIABLE HERE, the steps Alex performs to witness it.
2. **The triggers QA reported fired**, exactly as Beat 1 item 3: one marked
   `(caused by this branch)` put to him as a decision before the merge
   command; every other one a drafted `## Backlog` or `## Spotted` line for
   him to confirm or reject, whose `T<n>: backlog — …` commit lands before the
   Done commit, which stays the branch's last.
3. **The merge command**, ready to paste. Marking the task Done (status line,
   ticked boxes in its `## Tasks` block, his witness note under any
   UNVERIFIABLE criterion) is Alex's call (rule 7); once he makes it, the edit
   is the task branch's last commit, and it becomes true at the merge — Done is
   a claim about `develop`, so `develop` never shows the task Done while its PR
   is unmerged ([ADR-0014 §3](adr/0014-work-item-types.md#3-closing-a-task)).
4. **Anything still unpushed**, named — and, if the task changed the method, its
   row in [PORTING.md](PORTING.md)'s method-changes table, which is a task's
   only record.

No `main` move: the task reaches `main` with the next demoed story.

---

**What this is not.** A checklist Alex ticks is exactly the thing that failed for
S0: the DoD said the log was required, and it was skipped anyway, because a
self-attested list has no reviewer. The point of closeout is that the items
arrive *already done or already drafted*, so the failure mode is him rejecting
something rather than him forgetting it.

The closeout check in CI backstops the parts of this that leave artifacts in the
repo — a story under `## Done` with no log file, or with unticked criteria. It cannot see the demo, and this file cannot either.
Between them they cover the human gate as well as it can be covered; what remains
uncovered is exactly the part that requires a human holding a phone, which is the
whole reason the gate exists.

# S0 — Walking skeleton on the phone

**Asked for:** "I want to see a blank app running on my own phone before we
build anything."

**What came back:** exactly what was asked, and it was not enough. An Expo +
TypeScript project under `app/` with `strict` on, the title held as a pure
`screenTitle()` in `app/src/lib/appInfo.ts` so the one piece of logic was
testable and the component stayed dumb, three scripts wired for the machine
gate, and CI green on the PR. The dev agent correctly refused to claim AC2 and
AC4, reporting both as pending a phone it could not see — which is the only
reason the two defects below were found by the demo rather than smuggled past
it. Dependencies added: none beyond the template, plus `@expo/ngrok` as a
devDependency so the tunnel would not stop to ask for a global install.

**What QA caught:** nothing — QA was never dispatched for S0. That is the
honest entry. The dev agent self-reported, the dispatching session verified the
gate, and everything real was found by Alex on the phone. Both blocking defects
came out of the demo, in series, each one hidden behind the other:

1. **First scan failed on the SDK.** Expo Go refused the project outright. The
   scaffold had defaulted to SDK 57; the phone speaks 54 ([ADR-0007](../adr/0007-expo-sdk-pinned-to-expo-go.md)).
   Worth recording because the error blamed the wrong side: it read *"requires a
   newer version of Expo Go"* to a man who had installed Expo Go from the Play
   Store that day. The message points at the client when the project is the
   thing that is too new, and the instinct it provokes — go and update Expo Go —
   is a dead end on a device the Play Store is already capping.
2. **Only once that was fixed did AC4 become visible at all.** The repo sat on
   `/mnt/c`, where 9p delivers no inotify events, so Metro never saw a save
   ([ADR-0008](../adr/0008-repo-lives-on-wsl-ext4.md)). This could not have been
   observed earlier — the app had to render before anyone could watch it fail to
   change.

One consequence of that second failure is not in the ADR, and is the reason
this file exists.

**Fixing it broke the team.** Moving the repo to ext4 silently removed `po`,
`dev`, `qa` and `architect` from the session: Claude Code discovers
`.claude/agents/` from the project root at startup, and the running session was
still rooted at the old `/mnt/c` path, which by then held three signpost files.
Recovering the conversation then required launching from the *old* directory,
because session history is keyed to the path it started in. Neither fact is in
ADR-0008 and both cost a diagnosis cycle.

One process detail, since it bears on whether any of the above can be trusted:
the dispatching session reported `GATE EXIT: 0` once when the gate was red. The
cause was shell plumbing — `npm test` piped through `tail`, so the exit code
came from `tail`. It was caught and corrected in the same turn. But `CLAUDE.md` rule 3 calls a red
gate reported green the worst possible outcome, and this is how it happens in
practice: not by anyone lying, but by a pipe.

**What I'd specify differently:**

The tempting answer is that S0's AC were right as written, because a walking
skeleton exists precisely to find defects nobody could have named in advance,
and you cannot write an acceptance criterion for a failure class you have never
met. That defence holds for the *content* of both defects and I would not argue
against it.

It does not hold for their *shape*. AC2 and AC4 were both checkable only by
Alex, holding the phone. That gave the dev agent no way to falsify its own work
— it could do everything correctly and still be unable to tell, which is exactly
what happened twice. What was missing is not an AC that anticipates the bugs, but
an AC that moves the precondition off the phone:

- *Given the dev server is running, then the manifest Metro serves advertises an
  SDK version the Expo Go build on Alex's phone accepts.* Desk-checkable with
  `curl`, no phone required — and precisely the check the dev agent ran on the
  second pass to prove the downgrade worked. The verification existed; it simply
  was not required until after the failure had already cost a demo.
- *Given a source file is saved, then Metro logs a rebuild.* Would have caught
  the filesystem problem before anyone scanned a QR code.

Both are cheap, and both are of the same kind: an environment precondition
asserted at the desk, so that a phone-only AC fails for the reason it names
rather than for something underneath it. The pattern has already repeated once
— S1's equivalent was the `User-Agent` header, and that one was pre-empted.

**Method change:**

One, and it was found by an agent rather than by us. `.claude/agents/dev.md`
rule 5 forbade editing story statuses at all and delegated them to "the
manager's and QA's business" — but QA is read-only by design and holds no write
tool, so following the rule literally left no one able to move a story to
Review, and `CLAUDE.md` rule 7 permitting exactly that became dead letter. The
dev agent hit the contradiction, guessed, and said so in its report; that is the
good outcome, and the bad one is an agent silently picking the other reading.
Narrowed to: move your own story as far as Review, never to Done
(commit `d1d0be8`).

Nothing changed in `CLAUDE.md` or the DoD as a result of S0. Rule 8 and the
`po.md` changes made later in the same session belong to S1's refinement, not
here.

# S1 — Address search

**Asked for:** "I want to type an address, see matching results, pick one, and
have the app hold on to its coordinates."

**What came back:** roughly what was asked. A pure geocoding module
(`app/src/lib/geocode.ts`) that builds the Nominatim request, sets the required
`User-Agent` and maps `display_name`/`lat`/`lon` into candidates; a thin screen
that searches on explicit submit only, lists results with the ODbL attribution,
and holds the picked one in session state. Two passes, because the first failed
QA. Dependencies added: none — `fetch` was already in the runtime, which is what
[ADR-0009](../adr/0009-geocoding-via-nominatim.md) predicted.

**What QA caught:** AC3, and it mattered. Every outcome was cached, errors
included, so a search that failed in a tunnel was short-circuited forever — the
app displayed "check your connection and try again" and had already made trying
again impossible. It typechecked, passed 21 tests and had a green CI badge. That
is the whole argument for the review gate in one defect: an error path that fails
*politely* is invisible to a machine gate by construction. QA also flagged, without
failing them, a `flexShrink: 0` that is a no-op in React Native, a double-tap race
on the search button, and stale results surviving an edited field — all recorded in
`## Spotted`, unfixed.

**What I'd specify differently:** AC3 said "the previous **results** are shown
again" and I read that as covering the cache entirely. It does not say what happens
to a *failure*, and that silence is exactly where the defect lived. The ugly-input
question the playbook tells me to ask — "what would I hate to discover on a bus?" —
would have produced it: *given a search failed, when I try the same text again, then
it actually retries*. Note the shape: the AC covered the happy path and the error
path separately, but not the transition between them. Also worth pre-empting next
time: `limit=5` is set in ADR-0009 and surfaced during the demo as "why only five
results for `main street`?" — a decision recorded in the right place but invisible
from the screen it governs.

**Method change:** the largest of the story, and it was not in the app.
Every item below is **core** — none of it is about geocoding, Expo or phones,
which is why S1 moved the method further than the app.

The dispatching session recommended I run the phone demo *before* QA had reviewed,
offering QA afterwards as an option. The pipeline already fixes that order in three
places — `manager-playbook.md` step 6 before step 7, this document's review gate
before its human gate, and [ADR-0004](../adr/0004-git-flow-branching.md)'s meaning
for `develop` — and the session had read none of them. It was recommending from
memory. Root cause: the order lived only in `method/`, which is not auto-loaded,
while `CLAUDE.md`, which is, said nothing about it.

Changed as a result:
- `CLAUDE.md` **rule 9** — the pipeline is not reorderable, and a proposed next
  step must name which gate it is and whose.
- `CLAUDE.md` **rule 8** widened from "technology choice" to any inherited
  decision, and extended to the inverse error: proposing a deviation from a
  decision without first reading the ADR behind it. That was the session's second
  mistake in the same exchange — it suggested demoing the story branch before
  merge, which [ADR-0004](../adr/0004-git-flow-branching.md) had already ruled out
  for the parallel-agents case.
- `CLAUDE.md` gained **"The session Alex is typing at"**, and the standing-rules
  heading was widened from "all agents" to name it. The dispatching session is not
  a subagent, so nothing in `.claude/agents/` governed it, and nothing on paper
  stopped it implementing a story itself instead of routing to `dev`.
- [ADR-0010](../adr/0010-no-orchestrator-agent.md) — why that block lives in
  `CLAUDE.md` rather than a role file, and why an orchestrator subagent was
  rejected: Alex's two gates are interactive, and a subagent cannot hold a
  conversation.
- This document's **Human gate** reordered to match the playbook, and labelled a
  sequence rather than a set. It had listed the phone demo above the merge to
  `develop`, contradicting both the playbook and ADR-0004.
- This document's **merge clause** gained an explicit exception. I told the session
  to merge PR #2 for me, which the rule forbade outright. It flagged the conflict
  and complied. Rather than leave a rule that gets routed around, the clause now
  distinguishes its two jobs: an agent merging on its *own* judgement stays
  forbidden absolutely; an agent merging on my explicit instruction for a specific
  PR is allowed.

The pattern across all six: every one is a rule that was true, written down, and
in a file nobody had loaded. The fix each time was location, not wording.
